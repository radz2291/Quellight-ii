# UI stack evaluation and integration

Owner requested mature UI infrastructure before finalizing II-002, preserving the existing work and documenting a clear selection. The original candidate `498b9ea27dbd3f8c2bf4a8f04f92de9925a7fd89` used a native HTTP server, hand-managed DOM/messages/composer/cancellation and a small NDJSON consumer. It was not Next.js, assistant-ui or an equivalent mature chat runtime. Its apparent simplicity left this project responsible for chat state, cancellation and owner-switch races; the independent F1 finding demonstrates a real maintenance cost.

## Selection

Integrate **Next.js 16.4.3 App Router + React 19.3.1 + assistant-ui/react 0.15.31** in Cycle 1. Exact pins/lockfile are the authority. Current npm metadata lists React ^18 or ^19 peers for assistant-ui and Node >=20.9 for Next; the tested Node 22.22.3 meets that requirement. React/DOM and their types are pinned together. No provider/cloud service or paid calls are required.

assistant-ui LocalRuntime accepts a ChatModelAdapter for an existing custom streaming endpoint, owns message/thread/composer state and cancellation, and consumes cumulative content updates. The project's adapter only reads the existing NDJSON stream and forwards its abort signal. The maintained Thread/Message/Composer primitives provide the chat shell; no custom chat store, manual transcript DOM renderer or send/stop state machine is needed in the selected UI. Quellight's source/definition/record/history/run panels remain small typed React domain components; UI libraries cannot replace their product rules.

Next owns routing, React rendering, asset compilation and the web server. A streaming Route Handler forwards only local /api paths to the preserved authenticated gateway. It forwards cookies and origin checks, never receives a privileged database client, and does not cache authenticated responses. The gateway remains the source of authorization and durable commit acknowledgment; no browser credential or model SQL channel is introduced. Both processes bind loopback. Next telemetry is disabled by launch/build scripts. The original native UI remains versioned as a comparison/test fixture on the API service, while npm start selects Next. It is not a second production UI roadmap.

## Evidence and boundary

The owner's subsequent Companion-first clarification is a bounded presentation change: the default is conversation with a quiet Your space entry. Record schemas, explicit save forms, JSON/revisions and worker/run controls appear only in the secondary inspection view. Backend behavior and inspection capabilities are retained. Browser checks assert that architecture terms and detailed controls are absent from the default visible surface, then open Your space for the existing proof. The preview still truthfully labels synthetic responses; it does not imply real model/memory behavior.

Integration must pass a production Next build, strict TS/TSX checks, the existing DB/API tests and the same browser walkthrough via the Next route adapter, including streaming, stop/error, owner switching and lost acknowledgment. The retained F1 reproduction must pass for the selected UI and repaired original fixture. The final report records exact tested candidate and independent successor verdict; package presence alone is not integration proof.

The added dependency/build footprint is a deliberate trade for maintained UI infrastructure and a conventional future development path. No chat history persistence, multi-thread UI, tool-card rendering, markdown package, provider transport rewrite or full design system is claimed here. Before Cycle 2: keep the single selected Next/assistant-ui UI; add an owner-scoped history adapter only when conversation persistence/import is authorized, test source IDs and correction semantics across runtime changes, evaluate a maintained AI SDK transport if the provider protocol warrants it, and retire the comparison fixture after its regressions move entirely to the selected stack. No core data/worker changes are required merely to change the UI package.
