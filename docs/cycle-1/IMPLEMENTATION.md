# Cycle 1 implemented contract

This is the narrow local implementation, distinct from the broader [proposed contracts](../cycle-0/CONTRACTS.md). All data is synthetic. No Supabase account is connected.

## Boundaries and versions

Exact baseline: `a8c40fe74163b3273f603cab93453d86fb54bd1d`, on `codex/c1-core-vertical`. Node 22.22.3 / npm 10.9.8. Direct packages are exact-pinned and transitive dependencies/integrities recorded in the root lockfile: Mastra core 1.79.0, pg 8.23.1, zod 4.6.7; local tooling embedded-postgres 18.4.0-beta.17, TypeScript 5.9.3, Playwright 1.64.1. Installed with lifecycle scripts disabled. Windows binaries ran successfully without hydration; other platforms must inspect the published hydration script if needed. Embedded distribution is third-party tooling, not hosted Supabase or an official production installer.

The adapter choices retain the intended boundaries. A real Mastra `Agent.stream` runs the tool/model loop against a deterministic LanguageModelV3 implementation: first model turn calls discover, second emits two text chunks. It deliberately ignores user message meaning and never claims to have saved anything. No provider key, model HTTP endpoint, tracing exporter or Mastra server is configured. This is streaming/protocol proof, **not** conversational intelligence, memory, semantic retrieval, paid inference or GLM behavior.

The application owns durable queue/run/effect transactions; Mastra owns each bounded model/tool turn inside that worker. This does not replace the product architecture or select a production runtime. The beta Mastra durable wrapper is **NOT DEMONSTRATED**; its current docs warn that recovery can replay model/tool calls and require idempotent effects. Here the worker checkpoints after the bounded two-turn step; a crash before that checkpoint replays the read-only model/discover loop. No promise of exactly-once model invocation. See [Mastra durable agents](https://mastra.ai/docs/harness/durable-agents) and [run ownership](https://mastra.ai/docs/harness/durable-agents#run-ownership).

The native ES-module HTTP/browser shell is deliberately small for this vertical proof. Next.js/assistant-ui compatibility, provider adapters and production streaming UX remain future choices. This avoids adopting a second framework before its need is demonstrated, while leaving the API/model/database boundaries replaceable. The C0 chat-framework proposal was a candidate, not a committed dependency.

## Authentication and database permissions

Setup generates random local passwords for four roles: alice, bob, worker_alice, worker_bob. HTTP login verifies the supplied owner password against actual PostgreSQL SCRAM authentication; worker roles cannot log in through HTTP. A random HttpOnly, SameSite=Strict cookie identifies an in-memory eight-hour session. Server restart invalidates sessions; retained records survive. All state-changing HTTP requests require the exact loopback Origin and application/json; Host is checked against the bound loopback address. CSP disallows inline scripts, frames and third-party network assets. No browser receives database credentials. No runtime role owns tables, has BYPASSRLS/superuser, role membership, DDL or TRUNCATE rights.

RLS is ENABLED and FORCED on all eight owner-bearing tables. `ql.owner()` maps authenticated **session_user**, never mutable request fields, custom settings or user metadata. Alice and her worker resolve only to Alice; Bob and his worker only to Bob. Composite owner/id foreign keys prevent cross-owner provenance/run/effect references. Definitions and migration-version catalog are intentionally global read-only synthetic metadata. Read/write/subscribe tests execute against real PostgreSQL. SSE subscriptions poll owner-scoped RLS queries; they do not forward PostgreSQL NOTIFY payloads. Native Supabase Auth, Data API and Realtime are **NOT DEMONSTRATED**.

Only cancel/retry use narrow SECURITY DEFINER functions. They have fixed search paths, no dynamic SQL, revoked PUBLIC execution, explicit session_user-derived owner predicates, and no arbitrary data-returning authority. Direct user roles cannot update run/lease/outbox status; per-owner worker roles can. Runtime roles and private configuration are trusted server credentials, not a hostile arbitrary-SQL sandbox. Protect the ignored runtime file with user OS access controls; Windows does not enforce POSIX mode bits. Local OS/admin compromise is outside this proof.

Sources and revisions/events are append-only for runtime grants. Owner requests enter the strict validated gateway; direct database role tests exercise isolation, not a public arbitrary-SQL interface. Model receives only the schema-discovery tool. No raw SQL, owner override or privileged credential appears in its interface.

## Primitive and integrity contract

`discover {}` lists five primitives and active definitions; `query {kind?}` returns the most recent 100 visible records; `history {id}` returns visible source, revisions and events. `create {key,kind,data,source}` and `update {key,id,expectedVersion,data}` are strict envelopes. Unknown fields, kinds, invalid dates, oversized text, invalid UUIDs/keys and unrecognized typed fields are rejected. Dates are explicit ISO calendar dates; no unproven natural-language date parser. Create preserves the original source and writes record, revision, event and operation receipt in one transaction. Update preserves the source and prior revisions and locks/checks the expected version.

The bounded unit of atomic work is one record/source or one queue submission, not an unrestricted transaction program. Advisory owner+key transaction locks serialize duplicate submissions, canonical request fingerprints reject key reuse with different payloads, and the receipt commits with the effect. Acknowledgments occur after COMMIT. UI retains a digest/key for an unacknowledged save in sessionStorage, without retaining source/password text there; retry of unchanged input uses the same key. Owner scope is part of the pending-key namespace. Revisions distinguish human and Steward actors and retain operation and schema/skill references. The broader authority/lifecycle/link/search/approval model is not implemented.

`enqueue` is a separate run-control API using the same validation and operation receipts. Source, run, outbox, queued event and receipt commit atomically. Separate worker process claims a row with SKIP LOCKED, increments generation/attempt and sets a 1.5-second local-test lease; it renews every 400ms. Status derives `stalled` from an expired running lease. Reclaim increments generation. Every effect and completion locks the same live run row and checks status, generation and unexpired lease before modifying records. Effect+revision+event+unique effect receipt+run checkpoint commit together. Crash after that commit before terminal acknowledgment resumes without a second effect. Cancel increments generation; it prevents later effects, but cannot undo a previously committed record. Retry is explicit after sanitized failure. Replayed model work may repeat; applied local effects are deduplicated. No external side effects exist.

## Evolution and limitations

Migration 001 creates the generic spine and note/task definitions. Migration 002 adds seed_experiment schema v2 and its versioned skill reference; the matching [skill](../../extensions/seed-experiment/SKILL.md) documents interpretation limits. The gateway, model, worker and UI contain no seed-specific branch; fields render from definitions. V1 note/task readers and edit paths continue alongside v2 records. Empty-database up/down/up is tested; v2 down refuses to remove a kind with retained records/runs. This is intentional safe rollback requiring data disposition, not a claim of automatic lossy downgrade. No data-bearing core-schema teardown is exposed in the UI.

The skill is a versioned extension artifact/reference, not a demonstrated model-driven JIT skill search/load. Adding numeric/date primitives beyond the supported string/date/integer/boolean vocabulary, shared ownership, recurring schedules, embeddings, sensors, attachments or external actions requires additional validated capabilities. This proof does not provide V1 memory, historical import, production monitoring/scaling, distributed hosting or restore of a hosted service.

Primary security references checked during implementation: [PostgreSQL RLS](https://www.postgresql.org/docs/18/ddl-rowsecurity.html), [CREATE POLICY](https://www.postgresql.org/docs/current/sql-createpolicy.html), [Supabase RLS](https://supabase.com/docs/guides/database/postgres/row-level-security), [Supabase changelog](https://supabase.com/changelog), [embedded-postgres source](https://github.com/leinelissen/embedded-postgres). The changelog markdown index was fetched via HTTPS after the web reader rejected its content type. TLS-cipher and Postgres-update notices do not alter this isolated loopback proof; hosted compatibility must be rechecked before provisioning.
