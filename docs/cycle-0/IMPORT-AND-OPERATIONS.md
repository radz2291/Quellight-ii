## Destination and identity

Separate new project; initial development uses synthetic two-user fixtures. Source `persons` uses a legacy identity model; do not assume its UUIDs equal new Supabase Auth user IDs. An explicit private mapping links the owner-approved source person to a verified destination account. No guest/unrelated-owner data by default. Composite `(owner_id,id)` foreign keys and policies cover sources, records, events, revisions, links, runs, checkpoints, approvals, object metadata and subscriptions. Check both read and write paths; malicious owner changes and cross-owner links must fail.

Browser uses publishable credentials and user JWT; privileged worker credentials stay server-side with narrow grants and an audited capability boundary. Enforce policy on every primitive and at storage/database boundaries. SSR must validate claims/user via supported auth APIs rather than trust unvalidated cookie session objects. Grants control reachability; RLS controls rows. Exposed views need security-invoker semantics or revoked access. Do not use user-editable metadata for ownership. Queue rows are not browser-readable by default. See [RLS](https://supabase.com/docs/guides/database/postgres/row-level-security), [API security](https://supabase.com/docs/guides/api/securing-your-api), and [SSR guidance](https://supabase.com/docs/guides/auth/server-side/creating-a-client).

## Selective importer design

The [source audit](SOURCE-AUDIT.md) observes session-embedded message arrays, heterogeneous roles/content, no message IDs and two timestamp formats. Preserve source session ID + snapshot digest + array position as identity, original role/timestamp/content representation and original owner mapping. A simple role/content string copier would lose source meaning.

- **Private manifest:** approved source person/session set, exclusions, snapshot cutoff, canonical serialization/hash algorithm, field/role mapping version, eligible attachments, destination mapping and importer version. No actual manifest with private IDs is committed here.
- **Read phase:** bounded read-only repeatable snapshot of only approved rows. Store encrypted local/private archive if later export is authorized; preserve exact original representation plus digest. Stop on malformed content or ambiguous ownership. Do not log transcript bodies.
- **Map phase:** normalize `user`/`assistant` only where unambiguous. `user-with-attachments` retains its role and source link while a reviewed mapping may expose it as user. Preserve time/notes markers as source metadata, not automatically user assertions. Unsupported roles/parts go to quarantine, not silent drop. Thinking/tool/artifact parts are excluded from ordinary conversational memory until explicitly reviewed; do not reveal private reasoning or execute imported tools.
- **Time phase:** preserve epoch milliseconds and ISO strings verbatim; parse with strict format/range checks; source array order is canonical when timestamps tie. No original message ID exists; timestamp alone is not an idempotency key. Verify timezone before relative-date recall. Changed source array at the same ordinal creates a new snapshot/reconciliation case, never overwrites old evidence silently.
- **Write phase:** keyset batches (proposed 25 sessions / 1 MiB, whichever comes first), transaction per bounded chunk, deterministic unique source keys and persisted checkpoint. Retry returns existing receipts. If a source snapshot changes between batches, stop and reconcile; never merge new and old ordinals blindly.
- **Attachment phase:** separately inventory permitted embedded bytes/references; virus/type/size checks, content hashes, destination private objects and expiring links. Twenty-five attachment entries do not prove recoverable files. Do not follow arbitrary imported URLs during model execution. Never reuse a signed URL as a permanent source locator.
- **Reconcile phase:** compare approved source and destination sessions, per-role/per-part counts, original order, timestamp raw values, orphan links, quarantine counts and deterministic digests. Require explainable conservation: imported + quarantined + explicitly excluded = eligible source, by type and batch. Owner checks private samples in a secure viewer.
- **Curation phase:** separately bounded Steward pass after import review. Assistant suggestions and marker/tool metadata do not become user memories. Curated records cite original evidence and begin tentative where interpretation is uncertain.
- **Rollback:** import batch IDs fence writes; pause curation, revoke retrieval visibility and remove only records/projections/objects introduced by that batch with an audited inverse plan. Preserve owner edits and pre-existing records. Retain encrypted approved source/archive and import receipts within policy. Never roll back by deleting the old source project.

## Backups and retention proposal

Database backup and object backup are separate. Keep encrypted off-site destination backups with key custody, integrity manifest, access log, restore drills and policy-approved retention. Restore into isolation with outbound workers/schedules disabled, verify two-owner separation, source hashes, revision/operation receipts and object bytes, then release. Proposed RPO 24h and RTO 4h are targets for an initial rehearsal, not supported guarantees or measured results. Paid PITR or hosting upgrades require explicit budget authority. [Supabase backup limitations](https://supabase.com/docs/guides/platform/backups).

Proposal for owner review: retained source/curated records until correction/removal, redacted operational detail 30 days, durable minimal change receipts 1 year, rolling off-site backups 30 days. Sensitive prompt/response tracing disabled by default. Legal/owner obligations may change these periods. Forget requests immediately fence retrieval, invalidate caches and schedule projection/object deletion; backup expiry and restore-time tombstone replay are disclosed. A retained source archive is not exempt from authorized deletion policy.

## Resources, scheduling and cost

Use queue dispatch plus independent worker; queue visibility guarantees do not establish exactly-once effects. Edge Functions have finite runtime/resource limits, so they are a bounded ingress/dispatch option, not the default durable multi-turn host. [Queues](https://supabase.com/docs/guides/queues), [Edge limits](https://supabase.com/docs/guides/functions/limits).

Begin with one worker, per-owner concurrency 1, global 2, batch/token/payload limits and bounded retries; tune from measurements. Proposed per-run ceiling 12 model turns / 2 minutes before checkpoint/yield, 16k input tokens per turn, no automatic retries beyond three attempts, and owner-approved monetary ceiling before any inference. Reserve usage transactionally, then reconcile actual usage; hitting a cap yields visible waiting/failed status. Current allowed inference spend is $0. Future dollar amounts, model/host plan, destination capacity, queue lag and throughput are unresolved. Storage growth estimate must include source JSON, attachment bytes, embeddings, revisions and backup multiplier; 30.6 MB JSON is not an all-in capacity estimate.
